# План разработки: фиксы и новые фичи

Предложения по исправлению существующих проблем и развитию сервиса «Календарь звонков».
Документ разделён на две части: фиксы (баги, которые стоит поправить в первую очередь)
и новые фичи (развитие продукта). Фиксы описаны детальнее — со ссылками на код,
чтобы их было проще найти и исправить. Фичи — кратко, с ожидаемым результатом.

## Фиксы

### 1. Гонка при создании бронирования

Проверка пересечений интервалов выполняется в `build_booking`
(`backend/app/services.py:246`), **вне** блокировки `Store.add_booking`
(`backend/app/store.py:70`). При параллельных запросах два бронирования могут
одновременно пройти проверку «слот свободен» и оба записаться, создав
пересекающиеся встречи.

AGENTS.md обещает защиту «ограничением уникальности на уровне БД», но
фактически БД нет — данные хранятся в YAML-файле, а блокировка (`threading.Lock`)
не покрывает проверку пересечений.

**Как чинить:** сделать проверку пересечений атомарной вместе с вставкой
(перенести под блокировку), либо устранить гонку на уровне хранения
(см. фичу «Переход с YAML на SQLite» и уникальный индекс по слотам).

### 2. Фейковое подтверждение о брони

`frontend/src/components/guest/BookingModal.tsx:134` показывает гостю текст
«Подтверждение отправлено на {contact}», однако никакой отправки нет — ни email,
ни другого канала. Гость вводится в заблуждение.

**Как чинить:** либо убрать строку про отправку, либо реализовать реальное
уведомление (см. фичу «Реальные уведомления»).

### 3. Часовые пояса

Времена сериализуются без смещения (naive datetime, `2026-08-18T08:00:00`).
Фронтенд парсит их через `new Date(...)` и форматирует в часовом поясе браузера.
Если сервер (например, Railway, UTC) и браузер находятся в разных часовых поясах,
отображаемое время сдвигается относительно серверного.

**Как чинить:** согласовать представление времени между бэком и фронтом
(например, явный offset в сериализации) либо явно зафиксировать и
задокументировать, что время — серверное локальное.

### 4. Слоты не обновляются после конфликта 409

`useCreateBooking` (`frontend/src/api/endpoints.ts:83`) инвалидирует кэш слотов
только в `onSuccess`. При конфликте (409 «Слот уже занят») кэш не обновляется,
и занятый слот продолжает показываться как свободный до ручного обновления
страницы.

**Как чинить:** инвалидировать запросы слотов и на ошибку (onError/onSettled),
чтобы после 409 список слотов перечитывался.

### 5. Контакт гостя без проверки формата

Валидация `guestContact` в `backend/app/services.py:203` проверяет только
непустоту. Формат (email, телефон, telegram) не проверяется, что приводит к
недоступным для связи контактам.

**Как чинить:** добавить проверку формата контакта (как минимум email/телефон)
с человекочитаемым сообщением об ошибке.

## Новые фичи

1. **Удаление и редактирование типов событий** — PATCH/DELETE
   `/admin/event-types/{id}` и соответствующий UI на странице «Типы событий».
2. **Автоформируемый id типа события** — id генерируется на бэке (uuid),
   владельцу не нужно придумывать идентификатор вручную. **Меняет контракт API**:
   требуется правка `main.tsp`, перекомпиляция спецификации, регенерация
   `frontend/src/api/schema.d.ts`, обновление MSW-хендлеров
   (`frontend/src/test/mocks/handlers.ts`) и контрактного теста.
3. **Регистрация владельца** — страница регистрации/входа, сессия или токен
   вместо неявного разделения ролей по URL.
4. **Переход с YAML на SQLite** — замена хранилища `Store` на SQLite
   (SQLAlchemy или `sqlite3`), миграция существующих данных, уникальный индекс
   для защиты от гонок при бронировании.
 5. **Отмена и изменение брони** — DELETE и PATCH `/admin/bookings/{id}` и
    кнопки «Изменить» / «Отменить» на дашборде владельца. *(реализовано)*
6. **Пагинация и фильтры встреч** — на дашборде `/admin`: фильтр по дате и типу
   события, постраничная выдача.
7. **Экспорт встреч в iCal / Google Calendar** — генерация `.ics` для брони,
   ссылка добавления в календарь.
8. **Реальные уведомления** — отправка подтверждения о брони по email/telegram
   (устраняет фикс «Фейковое подтверждение»).
9. **Буфер между встречами** — настраиваемый перерыв между бронированиями.
10. **Статистика** — загрузка календаря, число встреч по типам событий и дням.
